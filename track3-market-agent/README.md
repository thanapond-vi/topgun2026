## ✅ ก่อนส่งงานทุกครั้ง (กติกาผู้จัด อัปเดต 15 พ.ย.)

- `python3 pack.py --send` หรือ `python3 pack.py` แล้วอัปโหลดที่ `<MARKET_URL>/handin` ภายใน 10 นาทีหลังตลาดปิด เมื่อทีมงานเรียก
- `handin.zip` ต้อง **ไม่เกิน 20 MB** (`pack.py` ตรวจให้และหยุดถ้าเกิน) ไฟล์เดี่ยวเกิน 5 MB ถูกข้าม ยกเว้นใน `logs/`
- กรรมการ **เทียบ `logs/decisions.jsonl` กับสิ่งที่ตลาดได้รับจริง** ดังนั้น
  - **ลบ `logs/` ที่เกิดจากการซ้อมก่อนเริ่มรอบเก็บคะแนน** ไม่งั้น log ของตลาดจำลองหรือตลาดฝึกจะปนอยู่ในไฟล์ที่ส่ง
  - ห้ามแก้หรือตัดต่อไฟล์ใน `logs/` เอง
- `.env` ต้องเป็น key แข่ง และ `pack.py` ไม่ใส่ `.env` ลง zip

## 📱 Dashboard ดูผลสด (ช่วงห้ามแตะเครื่องที่รัน agent)

ช่วงแข่ง 2–3 ต้องให้ agent ส่งคำสั่งเอง `dashboard.py` เปิดหน้าเว็บ **อ่านอย่างเดียว** ให้ดูจากมือถือหรือโน้ตบุ๊กอีกเครื่องได้

```bash
python3 dashboard.py              # พิมพ์ลิงก์ http://<IP เครื่อง>:8080/?t=<token>
```

- อ่านเฉพาะไฟล์ที่ agent เขียนใน `logs/` (`status.json`, `decisions.jsonl`, `memory-*.json`) **ไม่เรียก API ตลาดหรือ LLM เลย** และไม่มีปุ่มใด ๆ จึงส่งหรือแก้ข้อเสนอไม่ได้ และไม่กิน rate limit
- ลิงก์มี token สุ่ม เพราะทีมอื่นอยู่ในเครือข่ายเดียวกัน ถ้าไม่มี `?t=` จะได้ 403
- `main.py` เขียน `logs/status.json` ทุกรอบการอ่าน state (ถ้าเขียนไม่ได้ agent ยังทำงานต่อ)
- เปิด dashboard ก่อนเริ่มแข่ง แล้ววางเครื่องไว้ ส่วนการดูให้ใช้อีกเครื่อง
- **ถามผู้คุมงานก่อนวันแข่ง** ว่าเปิดหน้าดูผลจากอีกเครื่องได้หรือไม่ (กติกาห้ามส่งคำสั่งด้วยมือ ไม่ได้ห้ามดู แต่ควรยืนยัน)

| ส่วน | แสดงอะไร |
|:--|:--|
| แถบบน | phase, รอบ / ทั้งหมด, ป้ายปฏิทิน, เวลาที่เหลือ, LLM เปิดหรือปิด, อัปเดตล่าสุด (แดงถ้าเกิน 20 วินาที) |
| ภาพรวม | PR โดยประมาณ (ใช้ TV ของเรา), รายได้, กก. ที่ขายได้, ราคาเฉลี่ย, กก. ที่เสนอได้อีกในรอบ, ส่งผลประเมินแล้วหรือยัง |
| แจ้งเตือน | `strategy_crashed`, `batch_rejected`, `offer_rejected`, `state_error` และ agent หยุดอัปเดต |
| markup ที่เรียนรู้ | ต่อผู้ซื้อและต่อประเภท |
| ล็อต / ข้อเสนอที่เปิด / ผลรอบก่อน | ผลแต่ละซอง (`ACCEPTED`, `OUTBID`, `ABOVE_LIMIT` …) และสรุปตลาดต่อ RFQ |

## วิธีรัน

ทดสอบแบบเร็ว (ไม่ต้องเปิดเซิร์ฟเวอร์):
```bash
python3 mock/run_games.py --games 200
```
เทียบกับ starter และลองสภาพตลาดอื่น:
```bash
python3 mock/run_games.py --games 200 --strategy strategy_starter
python3 mock/run_games.py --games 200 --rival-kinds adaptive --ceiling-shift -0.1
```

ทดสอบเต็มวงจรผ่าน HTTP เหมือนวันแข่ง:
```bash
python3 mock/mock_market.py --round-seconds 4
```
แล้วเปิดอีก Terminal:
```bash
MARKET_URL=http://127.0.0.1:8765 TEAM_KEY=sk-T01-mock USE_LLM=0 python3 main.py
```
ดูผลหลังตลาดปิด:
```bash
curl -s -H "Authorization: Bearer sk-T01-mock" http://127.0.0.1:8765/v1/sandbox/reveal
```

## markup ที่เรียนรู้แยกตามผู้ซื้อ (`strategy.py`)

สร้างใหม่จาก memory ทุกรอบ (รีสตาร์ตแล้วได้ผลเท่าเดิม) ใช้สถานะของข้อเสนอที่ตลาดส่งกลับ:

| สถานะ | markup ของผู้ซื้อรายนั้นรอบหน้า |
|---|---|
| `ACCEPTED` | เพิ่ม `STEP_UP` (0.03) |
| `PARTIAL` | คงเดิม (อยู่ที่จุดตัดแล้ว) |
| `OUTBID` | ลด `STEP_OUTBID` (0.03) |
| `ABOVE_LIMIT` | จำไว้เป็นเพดาน แล้วอยู่ต่ำกว่าเพดานอย่างน้อย `CEILING_MARGIN` (0.02) ตลอดเกม |

- ค่าเริ่มต้นต่อประเภท: Specialty 1.15, Commercial 1.05, Instant 1.00 และบีบไว้ใน 0.85–1.50
- ผู้ซื้อที่ไม่เคยเจอใช้ค่าของประเภทเดียวกัน
- จัดลำดับ: ผู้ซื้อที่ markup สูงได้ล็อต TV สูงก่อน (ตามสไลด์วันที่ 18)
- ส่ง markup ที่เรียนรู้ให้ LLM เห็นใน prompt ด้วย

## ปฏิทินเทศกาลและ market_summary (`strategy.py`)

- `sell_budget()` แบ่งปริมาณตามป้ายของแต่ละรอบ: เทศกาล ×1.5, รอบซบเซาหรือใกล้ปิด ×0.7, ปกติ ×1.0 อ่านปฏิทินแบบยืดหยุ่นเพราะคู่มือไม่ได้บอกรูปแบบ JSON ของ `calendar` และส่งปฏิทินรอบถัดไปให้ LLM ด้วย
- `learned_markups()` มีตัวเลือก `STRATEGY_FILL_BONUS`: RFQ ที่ผู้ซื้อซื้อไม่ครบแปลว่าไม่มีคู่แข่งกดดัน จึงขึ้น markup เร็วขึ้น **ปิดไว้**
- ผลบน mock 300 เกม: ปฏิทิน PR 0.9437 เทียบ 0.9432 ก่อนใส่ (ต่างไม่เกินความแกว่ง) ส่วน fill bonus 0, 0.03, 0.06 ได้ผลเท่ากันทุกค่า เพราะ RFQ ใน mock ถูกซื้อเต็มทุกใบ (40 ทีมมีของเกินความต้องการ) สัญญาณนี้จึงไม่เคยเกิด
- ต้องทดสอบทั้งสองอย่างกับ sandbox ของผู้จัด ถ้ารูปแบบ `calendar` จริงต่างจากที่อ่านได้ `sell_budget()` จะกลับไปแบ่งเท่ากันทุกรอบเองโดยไม่ error

## สิ่งที่ mock เดาเอง (ต้องเทียบกับ sandbox)
