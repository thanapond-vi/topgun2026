## ✅ ก่อนส่งงานทุกครั้ง (กติกาผู้จัด อัปเดต 15 พ.ย.)

- `python3 pack.py --send` หรือ `python3 pack.py` แล้วอัปโหลดที่ `<MARKET_URL>/handin` ภายใน 10 นาทีหลังตลาดปิด เมื่อทีมงานเรียก
- `handin.zip` ต้อง **ไม่เกิน 20 MB** (`pack.py` ตรวจให้และหยุดถ้าเกิน) ไฟล์เดี่ยวเกิน 5 MB ถูกข้าม ยกเว้นใน `logs/`
- กรรมการ **เทียบ `logs/decisions.jsonl` กับสิ่งที่ตลาดได้รับจริง** ดังนั้น
  - **ลบ `logs/` ที่เกิดจากการซ้อมก่อนเริ่มรอบเก็บคะแนน** ไม่งั้น log ของตลาดจำลองหรือตลาดฝึกจะปนอยู่ในไฟล์ที่ส่ง
  - ห้ามแก้หรือตัดต่อไฟล์ใน `logs/` เอง
- `.env` ต้องเป็น key แข่ง และ `pack.py` ไม่ใส่ `.env` ลง zip

## 🧮 `advise.py` สำหรับช่วงขายด้วยมือ (ช่วงแข่ง 1 / 17 พ.ย.)

ใช้เมื่อกติกาให้คนกดเองบนหน้าเว็บ สคริปต์เรียกแค่ `GET /v1/state` กับ `GET /v1/calendar` ไม่ส่งอะไรเข้าตลาด

```bash
python3 advise.py          # หน้าจออัปเดตทุก 3 วินาทีจนตลาดปิด (Ctrl+C ออก)
python3 advise.py --once   # พิมพ์ครั้งเดียว
```

หน้าจอบอก:
- **ล็อต:** เกรด, TV/kg, ราคาต่ำสุดที่ไม่ควรขายต่ำกว่า (0.8 × TV), kg ที่เหลือขาย · ช่วง `APPRAISAL` บอกให้กรอก TV และเกรดตามตาราง
- **ผลรอบก่อน:** ข้อเสนอของเรา (ราคา, x TV, สถานะ) และราคาต่ำสุด/สูงสุด/เฉลี่ยของแต่ละ RFQ ในตลาด
- **แนะนำรอบนี้:** RFQ, ผู้ซื้อ, lot, kg, ราคา/kg และ x TV จากตรรกะเดียวกับ agent (`learned_markups` + `rule_plan` + `guard`) · RFQ ที่ไม่มีล็อตผ่านสเปก
- markup เรียนจาก **ราคาที่ทีมส่งจริง** ใน `last_results` จึงถูกแม้คนกดราคาต่างจากที่แนะนำ · จำผลไว้ใน `logs/advise-*.json` (ลบก่อนส่ง hand-in ตามหัวข้อด้านบน)

ทดสอบกับ mock 4 รอบแล้ว: อ่านทุกช่วงได้ แนะนำไม่ซ้ำกันระหว่างการรีเฟรชในรอบเดียวกัน และเรียน markup จากราคาที่ส่งจริง (ส่งแพงกว่าที่แนะนำ 5% ก็จำเป็น x1.07)

## 📱 Dashboard ดูผลสด (ช่วงห้ามแตะเครื่องที่รัน agent)

ช่วงแข่ง 2–3 ต้องให้ agent ส่งคำสั่งเอง `dashboard.py` เปิดหน้าเว็บ **อ่านอย่างเดียว** ให้ดูจากมือถือหรือโน้ตบุ๊กอีกเครื่องได้

```bash
python3 dashboard.py              # พิมพ์ลิงก์ http://<IP เครื่อง>:8080/?t=<token>
```

- อ่านเฉพาะไฟล์ที่ agent เขียนใน `logs/` (`status.json`, `decisions.jsonl`, `memory-*.json`) **ไม่เรียก API ตลาดหรือ LLM เลย** และไม่มีปุ่มใด ๆ จึงส่งหรือแก้ข้อเสนอไม่ได้ และไม่กิน rate limit
- ลิงก์มี token สุ่ม เพราะทีมอื่นอยู่ในเครือข่ายเดียวกัน ถ้าไม่มี `?t=` จะได้ 403
- `main.py` เขียน `logs/status.json` ทุกรอบการอ่าน state (ถ้าเขียนไม่ได้ agent ยังทำงานต่อ)
- เปิด dashboard ก่อนเริ่มแข่ง แล้ววางเครื่องไว้ ส่วนการดูให้ใช้อีกเครื่อง
- **ถามผู้คุมงานก่อนวันแข่ง** ว่าเปิดหน้าดูผลจากอีกเครื่องได้หรือไม่ (กติกาห้ามส่งคำสั่งด้วยมือ ไม่ได้ห้ามดู แต่ควรยืนยัน)

| ส่วน | แสดงอะไร |
|:--|:--|
| แถบบน | phase, รอบ / ทั้งหมด, ป้ายปฏิทิน, เวลาที่เหลือ, LLM เปิดหรือปิด, อัปเดตล่าสุด (แดงถ้าเกิน 20 วินาที) |
| ภาพรวม | PR โดยประมาณ (ใช้ TV ของเรา), รายได้, กก. ที่ขายได้, ราคาเฉลี่ย, กก. ที่เสนอได้อีกในรอบ, ส่งผลประเมินแล้วหรือยัง |
| แจ้งเตือน | `strategy_crashed`, `batch_rejected`, `offer_rejected`, `state_error` และ agent หยุดอัปเดต |
| markup ที่เรียนรู้ | ต่อผู้ซื้อและต่อประเภท |
| ล็อต / ข้อเสนอที่เปิด / ผลรอบก่อน | ผลแต่ละซอง (`ACCEPTED`, `OUTBID`, `ABOVE_LIMIT` …) และสรุปตลาดต่อ RFQ |

## markup ที่เรียนรู้แยกตามผู้ซื้อ (`strategy.py`)

สร้างใหม่จาก memory ทุกรอบ (รีสตาร์ตแล้วได้ผลเท่าเดิม) ใช้สถานะของข้อเสนอที่ตลาดส่งกลับ:

| สถานะ | markup ของผู้ซื้อรายนั้นรอบหน้า |
|---|---|
| `ACCEPTED` | เพิ่ม `STEP_UP` (0.03) |
| `PARTIAL` | คงเดิม (อยู่ที่จุดตัดแล้ว) |
| `OUTBID` | ถ้ารู้ราคาปิดสูงสุดของ RFQ (`price_max`) และต่ำกว่าราคาเรา: ตั้งต่ำกว่าราคานั้น `OUTBID_UNDERCUT` (0.01) · ถ้าไม่รู้: ลด `STEP_OUTBID` (0.03) |
| `ABOVE_LIMIT` | จำไว้เป็นเพดาน แล้วอยู่ต่ำกว่าเพดานอย่างน้อย `CEILING_MARGIN` (0.02) ตลอดเกม |

- ค่าเริ่มต้นต่อประเภท: Specialty 1.15, Commercial 1.05, Instant 1.00 และบีบไว้ใน 0.81–1.50
- **พื้นต่อรอบ (`markup_floor()`, เพิ่ม 17 พ.ย.):** ไม่เสนอต่ำกว่า `FLOOR_MID` (0.97) ตลอดเกม ช่วง 20% สุดท้ายพื้นไล่ลงหา `salvage_ratio` + 0.01 และถ้าขายช้ากว่าแผน (kg ที่เหลือ > ความจุต่อรอบ × รอบที่เหลือหลังรอบนี้) ลดพื้นเหลือ `salvage_ratio` + 0.01 ทันที · เหตุผลอยู่ใน `docs/bidding-strategy.md` หัวข้อ 10.3 ข้อ 5 และ 11
- **เปลี่ยนพื้นระหว่างแข่งได้โดยไม่แก้โค้ด:** `STRATEGY_FLOOR_MID=0.85 python3 main.py` (0.85 = พฤติกรรมเดิมก่อน 17 พ.ย.)
- จำนวนรอบอ่านจาก `round.of` ก่อน ถ้าไม่มีจึงใช้ `rules.timeline.rounds` (mock ตอบ timeline 8 รอบเสมอ ทำให้ผลทดสอบ 15 รอบก่อนหน้านี้คิดรอบที่เหลือผิด)

**ผลพื้น 0.97 เทียบพื้นเดิม 0.85 (mock 40 เกมต่อแถว แก้นับรอบแล้วทั้งคู่)**

|---|---|---|
| 40 ทีม 8 รอบ คู่แข่งผสม | 0.945 / 4.1 | 0.941 / 5.2 |

ได้มากเมื่อตลาดมีทีมใช้ starter ราคา 1.00 จำนวนมาก เสียเล็กน้อยในตลาดผสม (ต่างกันไม่เกิน sd ราว 0.03) ถ้าวันแข่งเห็นว่าคู่แข่งตัดราคาต่ำกว่า 1.00 กันมาก ให้ลด `STRATEGY_FLOOR_MID`

**ป้องกันเพิ่ม 17 พ.ย. (จากข้อสังเกตของ Gemini ที่ตรวจแล้ว)**
- `MAX_DROP = 0.05`: OUTBID ที่ใช้ `price_max` ลด markup ได้ไม่เกิน 0.05 ต่อรอบ เพราะ `price_max` เป็นบาท/kg ที่อาจมาจากล็อตทีมอื่นที่ TV ต่างจากของเรา · ตัวอย่าง: เสนอล็อต TV 120 ที่ x1.10 แพ้ล็อต TV 100 ราคา 105 บาท เดิมได้ 0.865 ตอนนี้ได้ 1.05
- กฎ "ขายช้ากว่าแผน" นับเฉพาะล็อตที่มี RFQ ในรอบนี้รับสเปกได้ · ตัวอย่าง: ล็อตที่ไม่ผ่านสเปกใดเลย 3,000 kg เดิมทำให้พื้นตกเป็น 0.81 ตั้งแต่รอบ 2 ตอนนี้คง 0.97 · ถ้าของที่ขายได้ล้นจริงยังลดเป็น 0.81 เหมือนเดิม
- mock 100 เกม 6 สภาพตลาด ผลเท่าเดิมทุกแถว (ต่าง ≤0.0001) เพราะใน mock `price_max` นับข้อเสนอที่แพ้ด้วยและแทบไม่มีกรณีล็อตขายไม่ได้ จึงทดสอบ 2 จุดนี้ด้วยกรณีที่สร้างเองแทน · ชื่อช่อง `round_capacity_kg` มีในคู่มือ API จริง (Gemini เข้าใจผิดข้อนี้)
- ผู้ซื้อที่ไม่เคยเจอใช้ค่าของประเภทเดียวกัน
- จัดลำดับ: ผู้ซื้อที่ markup สูงได้ล็อต TV สูงก่อน (ตามสไลด์วันที่ 18)

## ปฏิทินเทศกาลและ market_summary (`strategy.py`)

- `sell_budget()` แบ่งปริมาณตามป้ายของแต่ละรอบ: เทศกาล ×1.5, รอบซบเซาหรือใกล้ปิด ×0.7, ปกติ ×1.0 อ่านปฏิทินแบบยืดหยุ่นเพราะคู่มือไม่ได้บอกรูปแบบ JSON ของ `calendar` และส่งปฏิทินรอบถัดไปให้ LLM ด้วย
